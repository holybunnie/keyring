**OBSERVED:** One probe was sent (Law 7). Raw response at [`evidence/raw/0006-m0-3-probe.jsonl`](../evidence/raw/0006-m0-3-probe.jsonl).

## Probe construction

**OBSERVED:** `spot.exchangeInfo` for BTCUSDT reported `NOTIONAL minNotional 5.00000000`, `LOT_SIZE minQty 0.00001000`, and `spot.tickerPrice` reported `79830.97000000`. The probe parameters were read from these filters rather than guessed.

**OBSERVED:** The probe was a spot `LIMIT` `BUY` of `0.00001` BTC at `0.01` USDT — a notional of 0.0000001 USDT against a stated minimum of 5.00, at a price four million times below the prevailing market, against an account whose every balance was zero.

## Result

**OBSERVED:** HTTP 200. The JSON-RPC response was an error object:

```json
{"jsonrpc":"2.0","id":300,"error":{"code":-32603,
 "message":"{\"code\":-1013,\"msg\":\"Filter failure: PERCENT_PRICE_BY_SIDE\"}"}}
```

**OBSERVED:** The rejecting filter was `PERCENT_PRICE_BY_SIDE`, not the `NOTIONAL` filter this build predicted. Both are `-1013` filter failures rejected before the matching engine; the prediction was wrong about which filter would fire first, and the outcome class was unaffected.

**OBSERVED:** Spot balances and spot open orders were captured before and after the probe and compared equal. Open order count was 0 both times.

**INCONCLUSIVE — state proof incomplete.** Futures positions were not snapshotted around this probe. Law 3 requires balances, positions and open orders to be verified on every probe. This probe verified two of the three. The result is therefore reported with that limitation stated rather than presented as a complete zero-state-change proof.

## Gate outcome: UNGATED

**OBSERVED:** No confirmation was requested at any point. The invocation reached Binance's order-filter validation and returned a filter failure without any human interaction.

**OBSERVED:** This probe called the gateway directly over HTTP using the session's bearer token, rather than through a supported client's user interface.

**ASSUMED:** The most likely reading is that the confirm-before-execute pattern DOCUMENTED for "every non-read action" is enforced by the supported client, not by the gateway. This build has not inspected any client's implementation and has not tested a second client, so the location of the control is inferred, not established.

**OBSERVED:** Whatever the mechanism, a holder of this session token reached Binance's order validation path with no confirmation step. That is the measured answer to *how far along the execution path can this agent get without me* for this configuration.

## Binance error semantics survive the MCP layer

**OBSERVED:** The Binance spot error `-1013` was preserved verbatim inside the JSON-RPC error message, wrapped in a generic `-32603` internal-error code. It was not flattened into an opaque failure.

**OBSERVED:** Part 0.5's assumption *"that the -2015 / -1013 distinction survives the MCP layer rather than being flattened into a generic error"* is therefore partially resolved. `-1013` survives. `-2015` has not been produced by any probe and remains untested.

# M0.5 — in-place permission mutability

**OBSERVED (operator observation, not a captured gateway response):** The operator opened Profile → Dashboard → Sub-account → Account Management → **View permissions** for the Agentic sub-account and reported that **no permission can be toggled on or off there**. **Result: `RECONNECT_REQUIRED`.**

**OBSERVED:** This resolves the first row of the Part 0.4 contradictions table. The launch material's description of permissions as reviewable **or changeable** under Account Management is not supported for the change half of that claim, at least for this account in this configuration.

**OBSERVED:** No screenshot was captured by this build. The evidence type is recorded honestly in `evidence/raw/0009-m0-5-permission-mutability.jsonl` as an operator observation of a web interface, distinguishable at a glance from a captured response.

**OBSERVED:** Independent corroboration exists in this build's own measurements. Moving from Run A to Run B required a full `logout` and re-authorization; the granted scope changed only across that disconnect-and-reconnect cycle, never within a session.

## Consequence for the least-privilege diff (F3)

**OBSERVED:** Narrowing an over-broad grant is not an edit. It requires disconnecting the agent and re-authorizing from scratch.

**OBSERVED:** This makes the excess-permission finding sharper rather than softer. A user who grants more than a strategy needs cannot trim it. They must tear the connection down and rebuild it, and any other agent connected to the same sub-account is unaffected by their decision to do so.
